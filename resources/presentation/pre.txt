THE PROJECT IN ONE PAGE  (your ground truth — internalize this)
--------------------------------------------------------------------------------
WHAT IT IS: A signed-distance-field (SDF) editor. You place primitives (sphere,
box, cylinder, torus, etc.), combine them with boolean/CSG operations, light and
shade them, and it all renders in REAL TIME on the GPU, in the browser.

THE STACK:
- A C++ engine compiled to WebAssembly (WASM) via Emscripten. This is the
  authoritative core: it owns ALL state (the scene, the CSG tree, selection,
  per-object attributes, render settings).
- Rendering is done on the GPU through WebGPU, drawn straight to an HTML
  <canvas>. The shaders are written in WGSL.
- The UI is a React/TypeScript app. It is ONLY IO/UI. It holds NO authoritative
  data — after every change it re-reads a JSON snapshot from the engine and
  rebuilds its view.
- There is also a small native build (SDL + wgpu-native) used only for fast
  engine iteration.

THE ONE MENTAL MODEL (say this if asked "how is it architected?"):
  "The engine owns the truth; the UI is just a view." Data crosses the boundary
  two ways: CONTROL (JS calls a sdf_* C binding → an Application method → mutates
  a subsystem → re-uploads GPU buffers) and MIRROR (JS reads one big JSON
  snapshot of the whole scene and rebuilds its local mirror). New capability
  ALWAYS crosses through a sdf_* binding + the engine.ts facade — the web side
  never computes or stores domain truth.

HOW A PIXEL IS DRAWN (the heart of it):
  There is no mesh, no triangles. Every frame the GPU draws ONE full-screen
  quad (6 vertices). The FRAGMENT SHADER runs per pixel and does everything:
  it shoots a ray from the camera through that pixel and "ray marches" until it
  hits a surface defined by the SDF, then lights it. So the picture is computed,
  not rasterized from geometry.

04 — NE ÇÖZÜYORUZ (the problem). [MUST-KNOW] Why build an SDF editor at all?
     Key idea to sell: modeling with boolean operations (add/subtract/intersect
     solids) is natural and powerful, and SDFs make booleans trivial and exact,
     with no meshing and effectively infinite resolution. Real-time GPU feedback
     makes it interactive.

05 — NASIL ÇÖZÜYORUZ (the approach). [MUST-KNOW] The pipeline in one breath:
     represent shapes as SDFs → render them by ray marching in a fragment shader
     on the GPU → let the user edit a CSG tree → engine (C++/WASM) authoritative,
     UI (React) is a view, WebGPU does the drawing.

06 — BÖLÜM 02: Temel kavramlar (section divider).

07 — SDF: SIGNED DISTANCE FIELD. [MUST-KNOW, spend time]
     Concept: a function f(p) that returns the distance from point p to the
     nearest surface. SIGN convention: negative inside the object, positive
     outside, zero exactly on the surface. Primitives have exact analytic SDFs,
     e.g. sphere: f(p) = length(p) - r; box uses abs()/max on the components.
     KEY PROPERTY the whole renderer relies on: the SDF must return the true
     distance OR a conservative UNDER-estimate — never over-estimate — otherwise
     ray marching can step through a surface.
     Likely Q: "Neden SDF, neden mesh değil?" (answer in cross-cutting notes).

08 — RAY MARCHING (sphere tracing). [MUST-KNOW, spend time]
     Concept: from the camera, per pixel, shoot a ray. You don't know where the
     surface is, so you march: evaluate the SDF at your current point → that
     distance is a SAFE step size (a sphere of that radius is guaranteed empty)
     → step forward by it → repeat. Stop when the distance < hitEpsilon (HIT) or
     when you exceed maxDistance / maxSteps (MISS). This is why it's called
     "sphere tracing." Draw the picture in your head: big steps in open space,
     tiny steps as you graze a surface.
     Must be able to say: hitEpsilon, maxSteps, maxDistance are the three knobs;
     they trade quality for speed.

09 — CSG TREE. [MUST-KNOW]
     Constructive Solid Geometry: build complex shapes from booleans of simple
     ones. The math on distances is beautiful:
        UNION      = min(a, b)
        INTERSECT  = max(a, b)
        SUBTRACT   = max(a, -b)   (A minus B)
     SMOOTH versions replace min/max with a "smooth min" (a polynomial blend
     with a radius k) so shapes melt together instead of a hard crease.
     Structure: an n-ary tree. A node is a Primitive or an operation
     (Union/Subtract/Intersect/Group). Stored as a flat array with first-child /
     next-sibling links so an op can have any number of children.
     Design note worth mentioning: deleting a tree node "tombstones" it in place
     (never shifts the array) so all the links stay valid.

10 — RPN VE STACK MACHINE. [MUST-KNOW, spend time — this slide animates]
     Why: the GPU can't easily do recursion over a tree. So the engine COMPILES
     the CSG tree into a flat list of instructions in Reverse Polish Notation
     (postorder), and the shader runs it as a STACK MACHINE.
       - PUSH_OBJECT: evaluate one primitive's SDF, push the distance.
       - an OP: pop two distances, combine (min/max/smooth), push the result.
     The animation labels primitives A–E and shows the stack building up. A flat
     union of many objects keeps the stack shallow because each op fires right
     after its operand — n children → n-1 ops. IMPORTANT fact to say:
     "stack derinliği nesne sayısıyla değil, ağacın İÇ İÇE geçme derinliğiyle
     büyür." The GPU stack is a fixed size (16) with guards, so a malformed or
     too-deep program degrades safely instead of corrupting memory.
     The final step of the animation literally spells out the whole object's
     formula, e.g. ((A - B) ∪ ((C ∪ D) - E)).

11 — BÖLÜM 03: Mimari ve veri akışı (section divider).

12 — ARAYÜZ–MOTOR AYRIMI. [MUST-KNOW]
     The clean separation. Repeat the "engine owns truth, UI is a view" model:
     CONTROL path (JS → sdf_* binding → Application → subsystem → re-upload GPU)
     and MIRROR path (engine emits one JSON snapshot → UI rebuilds). Selling
     point: single source of truth, no state duplication, no sync bugs.

13 — C++ ENGINE. [MUST-KNOW some, rest nice-to-have]
     The Application "god object" owns subsystems by value: SceneManager (the
     primitive list + CSG tree), CsgTree (the tree + RPN compiler),
     EditorObjectStore (names/visibility/params that the raw GPU struct can't
     hold), SelectionState, Camera, GizmoController, SdfRenderer, serializers.
     THE ONE THING TO MEMORIZE HERE — the "three id spaces" (this is the single
     best question-defense in the whole talk):
        objectId    = a permanent identity for a primitive, never reused.
        nodeId      = a permanent identity for a CSG tree node.
        vector index= a primitive's CURRENT position in the array — TRANSIENT,
                      it shifts when you delete something.
     Rule: JSON, selection, and the outliner speak nodeId; the GPU pick buffer
     speaks vector index; you must convert carefully. Mixing them up is the #1
     source of bugs. If asked "hardest bug?", this is your answer.

14 — WEBGPU RENDERER. [MUST-KNOW, spend time]
     One full-screen quad; the fragment shader does all the work. The pipeline
     has THREE bindings: (0) a STORAGE buffer of scene objects, (1) a UNIFORM
     buffer of per-frame "globals" (camera, light, quality settings — a strict
     byte-for-byte struct shared with the shader), (2) a STORAGE buffer holding
     the compiled RPN program. It draws to TWO color targets at once: the visible
     image AND a hidden R32Uint "object-id" image (used for picking, slide 19).
     Efficiency point: buffers are REUSED across frames; if nothing resized, a
     steady frame is basically a single ~240-byte uniform write. Also: it's C++
     compiled to WASM via Emscripten; shaders are WGSL, baked into the build.
     Why WebGPU not WebGL: modern API, real storage/compute buffers, closer to
     the metal.

15 — IŞIKLANDIRMA (lighting). [MUST-KNOW, spend time — this is graphics]
     After a ray hits:
       - NORMAL from the SDF gradient: sample the SDF at 4 nearby points (a
         tetrahedron) and difference them. The gradient of a distance field IS
         the surface normal. (Great "aha" to explain: no stored normals, they
         fall out of the field for free.)
       - Blinn-Phong shading: ambient + diffuse (max(dot(n,L),0)) + specular
         (half-vector, shininess).
       - SOFT SHADOWS: march a second ray toward the light; if it nearly grazes
         geometry, penumbra. (IQ's soft-shadow trick.)
       - AMBIENT OCCLUSION: a few short probes along the normal; if the field
         says space nearby is crowded, darken the crevice.
       - Then ACES tone mapping + gamma. Detail worth one sentence: the canvas
         is NON-sRGB, so the shader gamma-encodes itself.
     Performance note (also sells the perf slide): shadows/AO are behind toggles,
     and "light off" (intensity 0) auto-skips the shadow march.

16 — ANTIALIASING. [MUST-KNOW — and know it's REAL, implemented]
     There's only one ray per pixel, so silhouettes would be jagged. The fix here
     is SSAA (supersampling): shoot an N×N grid of rays inside each pixel and
     average the color (aaSamples, clamped 1–8). Cost scales with N² — that's the
     tradeoff. Contrast with MSAA: MSAA can't help here because there's no
     rasterized geometry, just a full-screen quad; every pixel is a from-scratch
     ray march, so you must supersample.

17 — ARAYÜZ (React UI). [nice-to-have]
     One big React class component. After any mutation it calls refresh() to
     re-read the engine's JSON and rebuild. Render settings follow a fixed
     "5-layer chain" and ONE generic setter keyed by an id (not one binding per
     setting) — a clean-design point you can name-drop.

18 — BÖLÜM 04: Özellikler (section divider).

19 — OBJECT PICKING. [MUST-KNOW — cool, defensible]
     How do you click-select when there's no geometry to raycast on the CPU?
     Answer: that second render target. Each pixel already stored the winning
     object's index. On click, the engine copies that ONE pixel back from the
     GPU (async map) and reads the index → maps to objectId → to the top-level
     CSG node → selection. 0xffffffff means empty space. Note: mouse coords must
     be converted to real DEVICE pixels (render resolution can be scaled).

20 — GIZMO. [MUST-KNOW some]
     The move/rotate handles. Design highlight: the gizmo is DRAWN BY THE SHADER
     (not an HTML overlay), using the same camera basis as the rays, so it stays
     pixel-exact even while orbiting. The hover/drag logic lives in its own
     header-only state machine (GizmoController), decoupled from the engine. It
     writes color only, never an object-id, so you can't accidentally pick it.

21 — UNDO / REDO. [nice-to-have]
     Edits are wrapped in transactions (BeginSceneEdit/CommitSceneEdit) with a
     depth counter so a batch records ONE undo entry. Be honest about known gaps
     if asked: slider-drag/profile render-setting changes and group renames
     aren't individually undoable yet.

22 — DOSYA SİSTEMİ ve .sdfp FORMATI. [MUST-KNOW some]
     .sdfp is the project file. Layout: [magic + count][objects][CSG tree]
     [editor-attributes]. GOLDEN RULE to state: new data is APPENDED AT THE END
     and every reader is EOF-tolerant, so old files still open. The browser owns
     the real file via the File System Access API (Chrome/Edge only); the bytes
     cross the WASM boundary base64-encoded. Files are treated as UNTRUSTED: the
     CSG links are bounds-checked on load and a corrupt tree falls back to a flat
     scene instead of crashing.

23 — PERFORMANS ve RENDER AYARLARI. [MUST-KNOW — you'll likely get grilled here]
     The speed dials, in order of impact:
       - Render Resolution (50/75/100%): renders a smaller backing buffer and
         upscales. Cost scales with pixel count, so 50% ≈ 25% of the work. This
         is a pure display preference and lives WEB-SIDE, not in the engine.
       - Quality Presets (Fast/Balanced/High/Ultra): batch-apply resolution +
         toggles + the raymarch/shadow/AO budgets.
       - Toggles: Light / Shadows / AO gate the biggest optional per-pixel work.
       - FPS meter: it's vsync-capped, so it reads ~60 when there's headroom and
         is best for spotting DROPS, not for measuring absolute speed.
     The honest bottleneck story (have this ready): the shader evaluates EVERY
     object's SDF at EVERY march step — there is NO object culling, because a
     bounding-volume skip was tried and it CLIPPED real geometry (an SDF must
     never over-estimate distance), so it was reverted. Cost therefore scales
     with pixels × steps × objects. Honesty here impresses more than hand-waving.

CROSS-CUTTING "IMPRESS THE ROOM" POINTS  (weave these in; they earn credit)
--------------------------------------------------------------------------------
- "No geometry, everything is a function." The whole image is computed per pixel
  from math; there are no vertices, no triangles, no mesh. This is the headline.
- Normals, booleans, and blending all come from the DISTANCE FIELD itself for
  almost free — you don't store or compute them separately.
- Clean architecture: ONE authoritative core (C++), the UI is a disposable view.
  Single source of truth = no state-sync bugs.
- GPU-friendly design: recursion-free RPN program, fixed guarded stack,
  byte-for-byte CPU/GPU struct contracts, buffer reuse for a ~single uniform
  write per frame.
- Pixel-perfect picking via a second object-id render target — clever, and
  avoids CPU-side raycasting entirely.
- Honesty about tradeoffs (no culling because it clipped geometry; SSAA costs
  N²; FPS is vsync-capped) reads as engineering maturity, not weakness.

ANTICIPATED HARD QUESTIONS  (drill me on these; here are the crisp answers)
--------------------------------------------------------------------------------
Q: Neden SDF/ray marching, mesh yerine?
A: Booleans are exact and trivial (min/max), no meshing step, effectively
   infinite resolution, smooth blends for free, normals from the gradient.
   Tradeoff: cost scales with pixels and per-object SDF evaluations, and it's
   less natural for textures/arbitrary topology.

Q: Neden WebGPU, WebGL değil?
A: Real storage/compute buffers, a modern explicit API, better fit for pushing
   a scene buffer + an RPN program to the GPU.

Q: Neden C++/WASM, saf JS değil?
A: Performance and one authoritative native-style core we can also build
   natively for fast iteration; the browser layer stays a thin view.

Q: Nasıl seçim yapıyorsunuz, geometri yokken?
A: A second R32Uint render target stores each pixel's object index; we read back
   the clicked pixel from the GPU. No CPU raycast.

Q: En büyük performans darboğazı?
A: Every object's SDF is evaluated at every march step for every pixel; no
   culling (a bounds skip clipped geometry and was reverted). We manage it with
   render resolution, quality presets, and shadow/AO toggles.

Q: Smooth booleans nasıl çalışıyor?
A: Replace min/max with a smooth-min polynomial parameterized by a blend radius
   k; larger k = softer melt.

Q: Ağacı GPU'da nasıl yürütüyorsunuz?
A: We don't recurse on the GPU. We compile the tree to an RPN instruction list
   (postorder) and the shader runs it as a fixed-size stack machine.

Q: Bozuk/zararlı dosya sistemi çökertir mi?
A: No. CSG links are bounds-checked on load; invalid trees fall back to a flat
   scene; the GPU stack is guarded; loop counts are clamped.
