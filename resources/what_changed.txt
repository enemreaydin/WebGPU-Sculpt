================================================================================
 SDF EDITOR — WHAT CHANGED (ImGui  ->  React/WebAssembly)
================================================================================

Purpose of this file:
  A detailed, plain-language record of every change made to convert the project
  from a native C++ app with a Dear ImGui user interface into a web app where
  the UI is React (running in the browser) and the SDF engine is the same C++
  code compiled to WebAssembly (WASM) with Emscripten. Paste this to another
  agent (or read it yourself) to understand what was done and why.

--------------------------------------------------------------------------------
0. THE BIG PICTURE (READ THIS FIRST)
--------------------------------------------------------------------------------

BEFORE:
  - One native Windows program.
  - C++ did everything: created a window (SDL3), talked to the GPU (WebGPU via
    "wgpu-native"), rendered the SDF scene, AND drew the whole UI (menus,
    panels, buttons) using the Dear ImGui library.
  - The 3D scene was rendered into an offscreen texture, then ImGui displayed
    that texture inside one of its panels.

AFTER:
  - One web app that runs in the browser.
  - The SAME C++ engine (rendering, scene data, camera, save/load) is compiled
    to WebAssembly. It draws the SDF scene directly onto an HTML <canvas> using
    the browser's built-in WebGPU.
  - The UI is a separate React + TypeScript app (folder: web/). React draws the
    menus and panels as normal HTML/CSS around the canvas.
  - React and C++ talk to each other through a small "bindings" layer: React
    calls C functions exported from the WASM module (add object, move camera,
    save scene, etc.).
  - ImGui and ImGuizmo are completely removed.

Mental model of the running app:

    ┌───────────────────────────────┐    calls C functions    ┌──────────────────────────┐
    │  React (browser, HTML/CSS/TS)  │  ───────────────────>   │  C++ engine compiled to  │
    │  menus, object list, inspector │                         │  WebAssembly (WASM)      │
    │                                │  <───────────────────   │  raymarches SDF + CSG    │
    │  reads scene as JSON           │    returns scene JSON    │  draws onto <canvas>     │
    └───────────────────────────────┘                         └──────────────────────────┘

Key vocabulary:
  - Emscripten: a toolchain (compiler "emcc") that turns C/C++ into WebAssembly
    plus a JavaScript "glue" file that loads and runs it in the browser.
  - WASM (WebAssembly): a binary format the browser can run at near-native speed.
  - WebGPU: the modern browser API for using the GPU. The C++ code uses the same
    WebGPU calls whether native (through "wgpu-native") or web (through the
    browser). A thin C++ wrapper header, webgpu.hpp, hides the raw C API.
  - "bindings": C functions marked so JavaScript can call them.
  - "preloading": Emscripten packs files (our WGSL shaders) into a .data file
    and mounts them into a virtual, in-memory filesystem inside the browser so
    the C++ code can still open "/assets/shaders/main.wgsl".

--------------------------------------------------------------------------------
1. FILES DELETED (all ImGui-only UI code)
--------------------------------------------------------------------------------

These files existed only to draw the UI with ImGui/ImGuizmo, so they were removed:

  src/editor/Gui.cpp            - top-level "draw all panels" function
  src/editor/MainMenuBar.cpp    - File / Object / View / Settings menu bar
  src/editor/SettingsPanel.cpp  - the Settings window
  src/editor/Workspace.cpp      - the scene view + object properties panel,
                                  also hosted the ImGuizmo move-gizmo
  src/ui/AddObjectPanel.cpp     - the "Add Object" popup dialog
  src/ui/AddObjectPanel.h
  src/ui/Theme.cpp              - ImGui colors/fonts theme
  src/ui/Theme.h
  src/interaction/GizmoController.cpp  - ImGuizmo translate gizmo helper
  src/interaction/GizmoController.h

All of that UI functionality now lives in the React app (web/src/App.tsx).

--------------------------------------------------------------------------------
2. FILES ADDED
--------------------------------------------------------------------------------

C++ side:
  src/core/Vec2.h
      A tiny struct { float x, y; }. It replaces ImGui's "ImVec2" type, which
      the camera code used for mouse deltas. We no longer depend on ImGui just
      to have a 2-float pair.

  src/core/ViewportInput.h
      A struct describing one frame of viewport input (is the user orbiting?
      panning? how far did the mouse move? how much wheel scroll?). Input now
      comes IN from outside (from React), instead of the engine polling ImGui.

  src/bindings/WebBindings.cpp
      The bridge from JavaScript to C++. It defines plain C functions (all
      prefixed "sdf_") such as:
        sdf_add_primitive(type), sdf_remove_object(index),
        sdf_select_object(index), sdf_set_object_position/size/color(...),
        sdf_get_scene_json(), sdf_new_scene/open_scene/save_scene(),
        sdf_set_show_grid(on), sdf_resize(w,h),
        sdf_camera_orbit(dx,dy), sdf_camera_pan(dx,dy), sdf_camera_zoom(d).
      Each is marked EMSCRIPTEN_KEEPALIVE so Emscripten exports it for JS to
      call. They forward to the single global Application instance. This file
      is only compiled for the web build (wrapped in #ifdef __EMSCRIPTEN__).

React / web app (new folder: web/):
  web/package.json          - npm project + dependencies (React, Vite, TypeScript)
  web/tsconfig.json         - TypeScript config
  web/tsconfig.node.json    - TypeScript config for Vite's own config file
  web/vite.config.ts        - Vite (dev server + bundler) config
  web/index.html            - the HTML page shell
  web/src/main.tsx          - React entry point (mounts <App/> into the page)
  web/src/App.tsx           - THE UI: menu bar, object list, inspector panel,
                              the <canvas>, and mouse handlers for the camera
  web/src/engine.ts         - loads the WASM module and wraps the "sdf_*" C
                              functions in a friendly, typed TypeScript class
                              called Engine (engine.addPrimitive(), etc.)
  web/src/index.css         - base page styling (dark theme colors)
  web/src/App.css           - layout/styling for the editor UI
  web/public/engine/.gitkeep- keeps the output folder in git; the compiled
                              engine (sdf-engine.js/.wasm/.data) lands here

Docs / memory:
  README.md                 - rewritten for the new architecture (see below)
  resources/what_changed.txt- this file
  resources/running.md      - step-by-step build & run guide

--------------------------------------------------------------------------------
3. FILES MODIFIED (and exactly what changed in each)
--------------------------------------------------------------------------------

src/main.cpp
  - Removed the ImGui event handling (ImGui_ImplSDL3_ProcessEvent) and the
    ImGui header include.
  - Added a global pointer "Application* g_App" so the bindings layer can reach
    the running app instance from JavaScript.
  - Removed a duplicate "#define WEBGPU_CPP_IMPLEMENTATION" (that implementation
    is emitted once in WebGPUImpl.cpp; having it twice risks linker errors).

src/editor/Application.h  and  src/editor/Application.cpp
  This is the heart of the change. Application used to both run the engine AND
  drive ImGui. Now it is UI-agnostic:
  - Removed all ImGui includes, ImGui frame calls, the AddObjectPanel/Theme
    members, ImVec2 usage, and the ImGuizmo gizmo.
  - The render loop (MainLoop) now draws the SDF as a full-screen quad DIRECTLY
    onto the swap-chain/canvas surface. The old path (render to an offscreen
    texture, then let ImGui show it) is gone.
  - Added a clean "control API" that the bindings call:
        AddPrimitive, RemoveObject, SelectObject, GetSelectedIndex,
        SetObjectPosition/Size/Color, GetSceneJson, NewScene/OpenScene/SaveScene,
        SetShowGrid, CameraOrbit/Pan/Zoom, OnResize.
  - GetSceneJson() builds a JSON string describing all objects (index, id, type,
    position, size, color) plus the selected index and grid flag. React reads
    this to render its object list and inspector.
  - Camera input: instead of reading ImGui mouse state, it accumulates a
    ViewportInput each frame (set by CameraOrbit/Pan/Zoom) and feeds it to the
    CameraController, then clears it.
  - FindProjectRoot(): on the web build it just uses "/" (the virtual filesystem
    root where /assets is mounted). On native it still walks up folders to find
    the real assets/ + src/.
  - MainLoop(): on the web build it does NOT call surface.present()/device.poll()
    (the browser presents the canvas automatically); those remain native-only.

src/platform/GraphicsContext.cpp  and  .h
  - Windows.h is now included only on Windows (#ifdef _WIN32), so the file
    compiles for the web where there is no Win32.
  - InitializeSurface() now has two paths:
      * Web (Emscripten): create the WebGPU surface from the HTML canvas using
        the CSS selector "#canvas".
      * Windows (native): create it from the Win32 window handle (HWND), as before.
  - InitializeInstance(): on the web, Emscripten's wgpuCreateInstance REQUIRES a
    null descriptor and asserts otherwise; native accepts a descriptor. This is
    now branched so each platform gets what it needs.

src/camera/Camera.h / Camera.cpp
  - Replaced ImVec2 with our Vec2; removed the ImGui include. The math is
    unchanged.

src/camera/CameraController.h / CameraController.cpp
  - Rewritten to take a ViewportInput struct instead of polling ImGui/ImGuizmo
    for mouse buttons and drags. Same orbit/zoom/pan behavior, just fed from
    outside.

src/editor/Settings.h
  - Trimmed to only the values the engine actually uses (camera sensitivities).
    The UI-only fields (which settings tab is open, ImGui theme, fonts) were
    removed because the UI is now in React.

CMakeLists.txt  (the build script) — several changes:
  - Removed the imgui and imguizmo library targets and all references to them.
  - Removed Gui/MainMenuBar/SettingsPanel/Workspace/AddObjectPanel/Theme/
    GizmoController from the source lists; added WebBindings.cpp and the new
    core/ headers.
  - Native WebGPU backend pinned: the default backend downloads wgpu-native v24,
    whose API was rewritten and does NOT match this code. We force the older,
    matching backend (WGPU_STATIC, wgpu v0.19.x) for native builds. (Emscripten
    always uses its own WebGPU backend, so it is unaffected.)
  - Added the Windows system libraries that the static wgpu-native (a Rust lib)
    needs: ws2_32 userenv bcrypt ntdll opengl32 d3dcompiler propsys
    runtimeobject oleaut32. Without these the native link fails.
  - Emscripten output settings: when building for the web, the "main" target is
    emitted as web/public/engine/sdf-engine.js (+ .wasm + .data) with these
    important flags:
        -sMODULARIZE=1 -sEXPORT_NAME=createSdfModule  (so JS can create it)
        -sEXPORTED_RUNTIME_METHODS=ccall,cwrap,UTF8ToString (so JS can call in)
        -sALLOW_MEMORY_GROWTH=1  -sASYNCIFY  -sENVIRONMENT=web
        --preload-file <assets>@/assets  (packs the WGSL shaders into the app)
  - Post-build copies (fonts/assets/src next to the exe) are now native-only.

.gitignore
  - Ignore web/node_modules, web/dist, and the generated engine artifacts
    (sdf-engine.js/.wasm/.data).

4. BRING-UP BUGS WE HIT AND FIXED (useful to understand the gotchas)
--------------------------------------------------------------------------------

These are problems discovered while getting the web build to actually run. Each
is a real "web vs native WebGPU" or "Emscripten packaging" gotcha:

(a) Wrong Emscripten version.
    Symptom: compile error "webgpu/webgpu.h file not found".
    Cause: the installed Emscripten was 6.0.2, but the pinned WebGPU pieces and
    all our code use the older WebGPU API from the Emscripten 3.1.61 era. 6.x
    removed that header (it uses a different, newer WebGPU port).
    Fix: install and activate Emscripten 3.1.61 (see running.md).

(b) wgpuCreateInstance abort.
    Symptom (browser): Aborted(Assertion failed: descriptor == nullptr, at
    webgpu.cpp, wgpuCreateInstance).
    Cause: on the web, Emscripten's wgpuCreateInstance demands a NULL descriptor;
    our code passed a default (non-null) one.
    Fix: pass nullptr on the web build (GraphicsContext::InitializeInstance).

(c) Shaders "could not be read" (empty).
    Symptom (browser): [KRITIK]: Shader dosyalari okunamadi!
    Root cause: Emscripten fetched the preloaded ".data" package from the wrong
    URL. It resolves the .data relative to the PAGE (http://localhost:5173/
    sdf-engine.data) but the file is served from /engine/. So the .data 404'd,
    the virtual filesystem was empty, and every shader read returned "".
    Fix: in web/src/engine.ts, pass a "locateFile" function to the module that
    prepends "/engine/" to both the .wasm and the .data URLs. (The .wasm loaded
    fine on its own because it uses a different lookup — that was misleading.)
    Note: we also switched the C++ shader path to the absolute "/assets/..."
    while chasing this; that was harmless but the real bug was the .data URL.

(d) Render pass invalid — "depthSlice (0) is defined for a non-3D attachment".
    Cause: the browser's WebGPU (Dawn) requires the color attachment's
    "depthSlice" to be "undefined" for a normal 2D target; the zero-initialized
    default (0) is rejected.
    Fix: on the web build, set colorAttachment.depthSlice =
    WGPU_DEPTH_SLICE_UNDEFINED (that field only exists in the newer web header,
    so it is #ifdef'd for Emscripten only).

(e) Render pass invalid — "[TextureView] ... cannot be used with [Device]".
    Cause: React StrictMode (development mode) runs mount effects TWICE, which
    instantiated the WASM engine twice on the same canvas — two WebGPU devices,
    two render loops, fighting over one surface.
    Fix: removed <React.StrictMode> in web/src/main.tsx so the engine is created
    exactly once.

--------------------------------------------------------------------------------
5. WHAT STAYED THE SAME (the actual engine)
--------------------------------------------------------------------------------

None of the "brains" changed. These are unchanged in behavior:
  - src/renderer/SdfRenderer.*     GPU pipeline, buffers, shader loading
  - src/scene/*                    SceneManager, objects, CSG tree + RPN compiler
  - src/scene/data/*               plain data structs (SdfObjectData, Globals...)
  - src/serialization/*            .sdfo save/load
  - src/camera/Camera.*            camera math (only the ImVec2->Vec2 type swap)
  - assets/shaders/*.wgsl          the raymarching / SDF / CSG shaders

So: the rendering engine is identical; only the "who draws the UI and how does
input arrive" layer was replaced (ImGui -> React over a C bindings bridge), and
the platform layer learned how to target a browser canvas.

--------------------------------------------------------------------------------
6. HOW A USER ACTION FLOWS THROUGH THE SYSTEM (example: "Add Sphere")
--------------------------------------------------------------------------------

  1. User clicks "Sphere" in the React menu bar (web/src/App.tsx).
  2. App calls engine.addPrimitive(PrimitiveType.Sphere) (web/src/engine.ts).
  3. engine.ts uses Emscripten's ccall to invoke the C function
     sdf_add_primitive(0) inside the WASM module (src/bindings/WebBindings.cpp).
  4. That calls g_App->AddPrimitive(Sphere) (src/editor/Application.cpp), which
     asks SceneManager to add the object and refreshes the GPU scene buffer.
  5. React then calls engine.getScene() -> sdf_get_scene_json() to get the new
     object list as JSON and re-renders its panels.
  6. On the next animation frame, the C++ MainLoop redraws the SDF (now with the
     new sphere) onto the canvas. React never touches the pixels; the C++/WASM
     engine owns the canvas.
